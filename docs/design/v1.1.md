# Sleuthline 1.1 — design

Status: **implemented** (branch `feat/v1.1`), to be validated on the test VM before the 1.1.0 release. Differences with the draft are noted below.

Goal of 1.1: make the pipeline aware of **which evidence a case actually contains**, stop spending model calls where there is no data, and make two things measurable instead of trusting them: **data conservation** (nothing silently lost between a tool and the database) and **timestamp provenance** (how every time in the timeline was obtained).

Inputs to this design: the *Known limitations of 1.0* in the README, the runs on Case 001 (memory only, network only, full case) and the two external reviews (October 2026).

Out of scope for 1.1 (later versions): several hosts per case (1.2), the evidence & hypothesis graph, counter-evidence and finer confidence levels (2.0), the benchmark corpus and CI (continuous work).

---

## 1. Source detection: any combination of disk, memory and network

### Today
- `inventory.py` requires a KAPE collection at `<case>\` or `<case>\raw\` and stops otherwise. A memory-only or capture-only case needs an empty `C` folder.
- A collection in `<case>\kape\` (the natural name, used on the full case) is not found.
- Memory images (`<case>\memory\`) and captures (`<case>\pcap\`) are discovered by the orchestrator only.

### 1.1
`inventory.py` detects the three sources and writes them to a new file, `<case>\inventory\sources.json`:

```json
{
  "disk":    {"present": true,  "root": "C:\\...\\test04\\raw", "files": 2703, "integrity": "INTACT"},
  "memory":  {"present": true,  "images": [{"path": "...\\memory\\DESKTOP-SDN1RPT.mem", "bytes": 2147483648}]},
  "network": {"present": true,  "captures": [{"path": "...\\pcap\\case001.pcap", "bytes": 197583252}]}
}
```

- **Collection root**, in this order: `<case>\`, `<case>\raw\`, `<case>\kape\`, then any single sub-folder of the case that contains a `*_CopyLog.csv`. Two candidates: stop and name them (no guessing).
- **No collection, but a memory image or a capture:** the inventory succeeds with `disk.present = false`; `coverage.md` says so. No empty `C` folder.
- **Nothing at all:** stop with a clear message (as today).
- The orchestrator, `normalize.py` and `analyze.py` read `sources.json` instead of re-discovering. `normalize.py` copies it into the `meta` table (`sources` key), so the agent and the report see it.
- The SHA-256 of the memory images and captures stays where it is (parse step, `raw.vol_image`, `raw.pcap_files`); `sources.json` only lists them.

## 2. Steps that require a source

### Today
All 14 playbook steps call the model, even when the source a step is dedicated to is absent (step 4 *Memory* without a memory image, step 5 *Network* without a capture). The agent also does not know upfront which sources the case contains, and spends calls finding out that tables are empty.

### What the 1.0 runs show (why most steps must never be skipped)
A first draft skipped every step whose "usual" source was absent. Checked against the real runs, it would have lost important findings, because every source feeds almost every step (memory holds MFT records, registry, browser traces; a capture holds downloads, Kerberos / SMB, transferred files):

| Case | Step that the draft skipped | What it found |
|---|---|---|
| memory only | Triage of automatic detections | F-003 critical (code injected into `spoolsv.exe`), F-004 and F-005 high |
| memory only | Web browsing, downloads | F-021 high (`coreupdater.exe` downloaded with Edge) |
| network only | Program execution | F-007 critical, F-008 and F-009 high |
| network only | Persistence | F-012 high (C2 restarted at each logon) |
| network only | Files, anti-forensics | F-017, F-019, F-020 |

The only steps without any possible input are the ones **dedicated** to an absent source: step 4 without a memory image, step 5 without a capture (8.6 s and 0 findings on the network-only case).

### 1.1
- Each step of `PLAYBOOK.md` can declare the source it is dedicated to, on the line after its title:

  ```markdown
  ## Step 4: Memory (RAM)
  Requires: memory
  ```

  Syntax: `Requires: any` (default if the line is missing, so a custom playbook keeps working), `Requires: memory` or `Requires: network`. **Only steps 4 and 5 declare a requirement**; every other step stays `any` and always runs.
- A step whose required source is absent is **not sent to the model**. It is recorded with `status = "not_applicable"`, `reason = "no memory image"`, duration 0, no tokens, and appears in the report's step table and limitations.
- Safety rule, enforced by a test: a step is skipped **only** if it declares `Requires:` and that source is absent. No heuristic, no "probably empty" skip.
- The system prompt gets one line: `Sources in this case: memory image (DESKTOP-SDN1RPT.mem). No disk collection, no network capture.` and the agent gets the `coverage()` tool (section 3), so that inside every step it goes straight to the tables that have data instead of discovering empty ones.

Expected effect: small and safe. The real cost reductions come later (evidence graph in 2.0, a cheaper model for routine steps). Measurement: run the memory-only and network-only cases again and compare duration, cost **and findings** with 1.0; any finding lost is a regression.

## 3. Coverage, computed by the program

### Today
What was not collected, not parsed or found empty is described by the agent in its notes. The inventory knows what was collected; the orchestrator knows what each job produced; nobody puts the two together.

### 1.1
`normalize.py` builds a `coverage` table (one row per artifact family) from `inventory.json`, `parsed\jobs.jsonl` and the loaded tables:

| status | meaning |
|---|---|
| `not_collected` | the source or the artifact is absent from the case (e.g. no `Amcache.hve` in the collection, no memory image) |
| `not_covered` | collected, but no installed tool parses it |
| `not_parsed` | a tool exists but failed, was missing, or stopped (`failed`, `tool_missing`, `stalled`) |
| `empty` | parsed successfully, zero records (e.g. `vol_userassist`, a registry key incomplete in memory) |
| `analyzed` | records are in the database |

- Columns: `artifact`, `source` (disk / memory / network), `status`, `tool`, `rows`, `detail`.
- The agent gets a new read-only tool, `coverage()`, and the playbook rule: *"not found" may only be written for an artifact whose status is `analyzed`; otherwise state the coverage status.*
- The report gets a **Coverage** appendix (counts per status, then the `not_collected` / `not_parsed` rows), so that an empty section is never read as "nothing happened".

## 4. Conservation checks

### Today
`normalize_report.md` gives rows and rejected rows per file. Nothing compares them with what the tool produced, and a drop between the raw table and the timeline is only visible as a lower count.

### 1.1
A `conservation` table, filled at the end of `normalize.py`, with one row per output file and three checks:

1. **File → raw table:** records counted independently in the output file (CSV records, JSON lines) = rows loaded + rows rejected. Any other difference = `fail`.
2. **Tool → output**: Volatility (rows written per plugin, in `_run.log`) and Suricata (EVE lines, without the `stats` events, vs events per type after the split). Different = `fail`. *Implemented for these two only: their counts are written by Sleuthline itself; the EZTools counts (EvtxECmd, MFTECmd, PECmd) need their console formats to be checked first.*
3. **Raw table → timeline:** for each mapped table, records in the timeline vs records of the table. *Implemented as: a table whose date columns hold values but none of them gives a timeline row = `fail` (date format not understood); otherwise `ok`, with the number of records without a usable date in the note.*

- Columns: `src_file`, `check`, `expected`, `actual`, `status` (`ok` / `warn` / `fail`), `note`.
- `normalize_report.md` gets a **Conservation** section at the top: `ok` count, then every `warn` / `fail`.
- The report's traceability appendix states the result (e.g. *174 files, 0 loss*).
- A `fail` does not stop the normalization (a documented gap is better than no database), but it is listed in the report's limitations.

## 5. Timestamp provenance

### Today
The timeline has `ts` (UTC) and `ts_desc`. The conversion of local times is only appended as text to `ts_desc` (`[local time converted to UTC, ActiveTimeBias=420 min]`), and the raw value is not kept.

### 1.1
Four new timeline columns, filled in `insert_timeline`:

| column | content |
|---|---|
| `ts_original` | the raw value as written by the tool (e.g. `2020-09-19T04:39:58.412735+0200`, `9/19/2020 3:40:49 AM`) |
| `ts_conversion` | `utc` (already UTC), `offset` (explicit offset in the value, e.g. Suricata), `local_bias` (local time, converted with the host's ActiveTimeBias), `auto` (auto mapping, not validated) |
| `ts_tz_detail` | e.g. `+02:00`, `ActiveTimeBias=420 (Pacific Standard Time, value at collection time)` |
| `ts_confidence` | `high` (`utc`, `offset`), `medium` (`local_bias`: DST changes during the period are not handled), `low` (`auto`) |

- `ts` itself does not change: no regression for the agent's queries or the golden references.
- A fifth column, `clock_offset_s`, is created **empty** in 1.1. It is reserved for the clock offset between sources (capture vs host), which 1.2 / 2.0 will compute. The agent found the one-hour offset of Case 001 by itself; the program will do it later.
- The `[local time converted…]` suffix of `ts_desc` is removed (now in `ts_tz_detail`).
- Cost: about +15 % of database size on the full case (estimate, to be measured).

## 6. Small fixes found during the 1.0 tests

| Issue | Fix |
|---|---|
| Parse summary shows the sum of the Volatility plugin durations (1,633 s for 10 min 39 s) | `duration_s` = elapsed time of the job; the sum is kept as `cpu_s` |
| Volatility warnings (registry keys incomplete in memory) not in the job status | `WARNING  volatility3` added to the warning patterns of the `volatility` job |
| Suricata: `threshold.config` missing (not in the MSI) | an empty `threshold.config` written next to `_suricata.yaml` |
| Suricata: 9 ET Open rules rejected (`file.magic`, not in the Windows build) | rules that fail to load are counted from `suricata.log` and reported in the job note; no change to the rules |
| Report shows `?` as main system without a KAPE collection | fallback: `COMPUTERNAME` from `raw.vol_envars`, else `?` (*the captures do not give a reliable host name: dropped*) |

## 7. Positioning

README tagline, as suggested by the second review: *"a DFIR evidence platform with an AI investigation layer"*. The LLM is one layer on top of deterministic tools and a common evidence database.

## Tests (new)

- Source detection: collection at the root, in `raw\`, in `kape\`, in another single sub-folder; two candidates (error); memory only; capture only; nothing (error).
- Step requirements: parsing of `Requires:`; missing line = `any`; a memory-only case skips only step 5 and a network-only case only step 4, without any model call (mock provider: call count); every step without `Requires:` runs whatever the sources.
- Coverage: one artifact in each status, from a fake inventory and fake jobs.
- Conservation: a CSV with one row the normalization drops (fail), an EVTX count that differs (warn).
- Timestamp provenance: one UTC source, one with offset (Suricata EVE line), one local-time source with ActiveTimeBias; `ts` unchanged, the four columns filled.
- The existing 49 tests keep passing; the golden references are updated only for the new columns.
